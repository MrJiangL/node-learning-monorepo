# Project 编辑删除体验优化 smoke 和复盘

## 1. 这次我验证了什么

这次 smoke 复盘验证的是 Project 编辑删除体验优化是否真的让用户操作更稳定、更清楚、更可恢复。

上一轮已经把 Project 编辑 / 删除主链路做通：

```text
创建 Project
  -> 编辑 Project
  -> 删除 Project
  -> Activity Log 记录
  -> 线上 smoke 验证
```

这一轮不是继续加新接口，而是检查体验层是否更像一个真实产品：

- 删除不再突然弹出浏览器原生 `confirm`
- 删除前会在当前 Project item 内展示确认区
- 取消删除不会误删 Project
- 确认删除才会真的触发删除
- 保存 Project 时能看到“保存中...”
- 删除 Project 时能看到“删除中...”
- 保存失败后不会退出编辑态
- 保存失败后用户刚输入的内容不会丢
- 删除按钮和确认删除按钮有更明确的危险操作样式

这次优化背后的核心判断是：

```text
CRUD 功能不是只要请求成功就结束。
用户还需要知道自己正在做什么、操作有没有进行中、失败后能不能恢复。
```

从实现和本地验证结果来看，这一轮体验优化已经达到了当前阶段目标。

## 2. 页面内删除确认比 confirm 好在哪里

页面内删除确认比浏览器原生 `confirm` 更适合当前 Project 工作台。

原来的交互是：

```text
点击删除
  -> 浏览器弹出 confirm
  -> 用户确认或取消
```

这个方式虽然简单，但有几个问题：

- 弹窗样式由浏览器控制，和页面视觉不一致
- 用户的注意力会被突然打断
- 不方便展示更多上下文
- 不方便加 loading、错误、说明文案
- 后续如果要做更复杂交互，会比较受限

现在改成页面内确认后，交互变成：

```text
点击删除
  -> 当前 Project item 内出现确认区
  -> 用户点击确认删除或取消删除
```

这个体验更清楚。

因为确认区就出现在将要被删除的 Project 下方，用户知道自己正在处理哪一个 Project。

这也是一个重要的产品设计点：

```text
危险操作的确认，最好贴近被操作对象。
```

它让用户不需要在脑子里额外记：

```text
我刚刚点的是哪一个删除？
```

页面内确认还有一个好处：后续很容易继续扩展。

例如可以加：

- Project 名称高亮
- “删除后 Todo 也会被删除”的提醒
- 删除失败错误提示
- 更细的 loading 状态
- 未来的 undo 或软删除提示

所以这一步不仅是体验优化，也是在给后面的产品迭代留空间。

## 3. saving / deleting 状态解决了什么问题

`saving` / `deleting` 状态解决的是异步操作期间的“不确定感”和“重复点击”问题。

在前端里，用户点击按钮之后，请求不会瞬间完成。

如果没有 loading 状态，用户会看到：

```text
点击保存
  -> 页面好像没反应
  -> 用户可能再点一次
  -> 可能重复发请求
```

或者：

```text
点击确认删除
  -> 页面好像没反应
  -> 用户可能连续点删除
```

这不是用户“不懂”，而是界面没有给反馈。

现在保存时会显示：

```text
保存中...
```

删除时会显示：

```text
删除中...
```

并且按钮会 disabled。

这解决了两个问题：

1. 用户知道操作已经开始了
2. 前端减少重复提交的风险

这里还有一个分层上的学习点。

这一轮把真实异步状态放在页面层：

```text
ProjectsPage
  -> savingProjectId
  -> deletingProjectId
  -> projectMutationError
```

而不是让 `ProjectListPanel` 自己猜 API 状态。

这是合理的。

因为真正发请求的是页面编排层，不是展示组件。

`ProjectListPanel` 只负责：

```text
展示 saving / deleting 状态
根据用户点击 emit 事件
维护编辑态和删除确认这种本地 UI 状态
```

这个边界会让组件更好测，也更不容易和 API 细节耦合。

## 4. 保存失败保留输入为什么重要

保存失败保留输入，是这一轮里非常关键的体验点。

用户修改 Project name / description，本质上是在投入脑力：

```text
我要怎么命名？
描述怎么写更清楚？
这段文字要不要调整？
```

如果点击保存后失败，然后页面退出编辑态或者清空输入，用户会有一种很差的体验：

```text
失败了，而且我刚刚写的东西也没了。
```

这比单纯的请求失败更让人沮丧。

现在更合理的行为是：

```text
保存失败
  -> 仍然停留在编辑态
  -> 保留用户输入
  -> 展示错误提示
  -> 用户可以修改后重试
```

这背后的产品原则是：

```text
失败不可怕，失败后可恢复才重要。
```

这也是表单体验里很基础但很容易被忽略的一点。

尤其是未来如果表单变复杂，比如 Project 有更多字段，失败后清空输入会造成更大的损耗。

所以现在提前把这个模式练起来，是值得的。

## 5. 当前体验还可以继续怎么优化

当前体验已经比第一版好很多，但还可以继续优化。

可以考虑的方向有：

1. 更细的错误提示

   现在错误提示主要来自 API 返回信息。后续可以区分：
   - 未登录
   - Project 名称为空
   - 网络错误
   - 后端 500
   - Project 已被删除

2. 删除确认文案更具体

   现在是：

   ```text
   确定删除这个 Project 吗？
   ```

   后续可以变成：

   ```text
   确定删除「xxx」吗？这个操作会同时删除它下面的 Todo。
   ```

3. 用户级 Activity Log

   现在 Activity Log 主要依赖当前选中的 Project。

   Project 删除后，页面会清空 selectedProjectId，所以不适合继续在 Project 面板里看 `project.deleted`。

   如果要查看删除历史，更合适的是做：

   ```text
   用户级 Activity Log
   ```

4. Todo dueDate 展示和编辑

   Project 主体能力已经比较完整，下一步也可以补 Todo 的时间字段，让 Todo 更接近真实任务管理。

5. 线上体验 smoke

   体验优化涉及真实用户交互，尤其是页面内删除确认和 loading 状态。

   本地通过后，仍然值得部署到 Netlify 做一次线上 smoke。

## 6. 下一阶段我选择什么

我建议下一阶段选择：

```text
A. 部署上线和线上 smoke
```

原因是这一轮虽然没有改后端 API，但改的是用户操作 Project 编辑 / 删除时的关键交互。

它影响的是线上真实用户的数据操作体验：

```text
用户是否能安全取消删除
用户是否能看到保存中 / 删除中
用户保存失败后输入是否还在
用户是否能明确识别删除是危险操作
```

这些都应该在线上环境里验证一次。

更稳的节奏是：

```text
本地体验优化完成
  -> 本地测试 / typecheck / build 通过
  -> 部署到 Netlify
  -> 在线上验证页面内删除确认
  -> 在线上验证取消删除
  -> 在线上验证确认删除
  -> 在线上验证保存中 / 删除中状态
  -> 如失败，用 X-Request-Id 串 Railway logs
```

这一步完成后，再进入业务功能会更踏实。

如果现在直接跳到 Todo dueDate 或用户级 Activity Log，也可以，但会留下一点隐患：

```text
刚改过的线上交互还没真实验证。
```

所以我建议先把体验优化部署上线并 smoke。
