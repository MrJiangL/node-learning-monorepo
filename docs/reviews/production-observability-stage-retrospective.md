# 生产化监控阶段复盘

## 1. 这一阶段我完成了什么

这一阶段我把项目从“线上能访问”推进到了“线上出问题时有基本排查线索”。

我完成了：

- Railway API 部署
- Railway MySQL 接入
- Netlify 前端部署
- 前后端线上联调
- `/health` 健康检查
- `/ready` 数据库 readiness check
- error handler 服务端日志增强
- Request ID 日志串联
- 浏览器 Network 到 Railway logs 的排障路径复盘
- 线上注册 / 登录 / 退出 smoke
- 前端产品体验主路径验证

这一阶段的重点不是多写了几个接口，而是开始建立一种生产化意识：

    线上功能能跑，只是第一步。
    真正上线后，还要能判断服务是不是活着、依赖是不是正常、错误该怎么定位。

现在我已经有了基础的“线上维护视角”。

## 2. /health 解决了什么问题

`/health` 解决的是：

    API 进程还活着吗？

它更像一个非常轻量的生命体征检查。

如果 `/health` 能返回成功，说明至少这些事情成立：

- Railway 上的 API 服务正在运行
- Express app 能接收 HTTP 请求
- 路由注册基本正常
- 进程没有直接崩掉

但 `/health` 不代表完整业务一定可用。

因为它通常不检查数据库、不检查外部依赖，也不保证登录、创建 Project、创建 Todo 这些业务路径都能成功。

所以 `/health` 的定位是：

    看 API 进程是否在线。

它适合做最基础的 uptime check，但不能单独证明整个系统可用。

## 3. /ready 解决了什么问题

`/ready` 解决的是：

    API 进程和关键依赖是否都准备好了？

相比 `/health`，`/ready` 更接近真实业务状态。

因为当前项目的大多数核心接口都依赖数据库：

- 注册账号要写数据库
- 登录要查用户
- 创建 Project 要写数据库
- 创建 Todo 要写数据库
- Activity Log 也要写数据库

如果 API 进程还活着，但数据库连接失败，那么 `/health` 可能还能成功，而真实业务已经不能正常使用。

所以 `/ready` 要检查数据库连接。

我现在对两者的理解是：

```text
/health：进程是否活着
/ready：服务是否准备好处理真实业务请求
```

这里的关键学习点是：

    健康检查不等于业务可用。
    Readiness 比 health 更接近真实依赖状态。

## 4. error handler 日志解决了什么问题

error handler 服务端日志解决的是：

    后端发生未预期异常时，开发者能不能看到足够线索。

前端响应应该克制，不能把 stack trace、数据库细节、环境变量信息暴露给用户。

但服务端日志需要保留排查信息。

一个有用的 error handler 日志应该帮助我看到：

- 哪个请求出错
- 对应的 requestId 是什么
- 错误类型是什么
- 错误信息是什么
- stack 从哪一层代码抛出来
- 最终响应状态码是什么

它解决的是“后端为什么炸了”的问题。

如果用户只看到：

```text
创建 Project 失败
```

那对用户是足够友好的。

但开发者还需要在服务端看到更细的信息，比如：

```text
requestId: xxx
errorName: PrismaClientKnownRequestError
errorMessage: ...
stack: ...
```

所以我现在理解的边界是：

    用户侧响应要安全、简洁。
    服务端日志要详细、可排查。

## 5. requestId 解决了什么问题

requestId 解决的是：

    怎么把一次请求在不同地方的线索串起来。

浏览器 Network 里能看到失败请求。

Railway request logger 里能看到请求结果。

Railway error handler 里能看到异常细节。

如果没有 requestId，我只能靠时间、路径、状态码去猜这些日志是不是同一次请求。

有了 requestId 以后，我可以从浏览器响应头拿到：

```text
X-Request-Id: xxx
```

然后去 Railway logs 里搜索同一个值。

这样就能把：

```text
浏览器里的失败请求
  -> request logger 里的请求记录
  -> error handler 里的异常日志
```

串成一条线。

但 requestId 不是监控平台。

它不能自动发现故障，不能自动报警，也不能统计错误率。

我现在对它的定位是：

    requestId 不是发现问题的工具，而是定位某一次请求的线索编号。

## 6. 浏览器 Network、Railway logs、Request ID 怎么配合

现在我的线上排障路径是：

1. 用户反馈某个页面或动作失败，比如创建 Project 失败。
2. 我先打开浏览器 Network，而不是直接看代码。
3. 在 Network 里找到失败请求。
4. 看请求 URL，确认它是不是真的打到了 Railway API。
5. 看 method，确认是不是预期的 `POST /projects`。
6. 看 request headers，确认有没有带 Authorization。
7. 看 status code，判断是 400、401、403、404、500，还是 network error。
8. 看 response body，确认后端有没有返回错误码和 message。
9. 看 response headers 里的 `X-Request-Id`。
10. 去 Railway logs 搜这个 requestId。
11. 先看 request logger：method、path、statusCode、durationMs。
12. 再看 error handler：errorName、errorMessage、stack。
13. 如果没有后端日志，回头查前端请求是否真正发到了 API。
14. 如果是 500，再继续查数据库、环境变量或代码异常。

这条路径让我从“凭感觉排障”变成了“顺着证据排障”。

这里最重要的思维变化是：

    先定边界，再查原因。

Network 负责帮我判断请求是否发出、发到哪里、后端是否响应。

Railway logs 负责帮我判断后端收到请求后发生了什么。

Request ID 负责把这两边连起来。

## 7. 当前还缺哪些真正的监控能力

虽然现在已经有了基础排障能力，但还不能说监控体系完整。

当前还缺这些能力：

### 自动发现故障

现在更多是用户说出问题后，我再去查。

但真实线上系统更希望：

    服务刚挂，我就知道。

这需要 uptime monitor 或外部健康检查。

### 自动报警

现在没有邮件、短信、Slack、飞书这类告警。

如果服务半夜挂了，我不会自动收到通知。

### 错误率统计

现在能查某一次错误，但不能方便地回答：

```text
过去 1 小时 500 错误有多少？
哪个接口错误最多？
错误率是否突然升高？
```

这需要结构化日志、指标系统或 APM。

### 慢请求趋势

request logger 有 durationMs，但还没有慢请求阈值，也没有趋势统计。

现在我能看到某一次请求慢，但不能系统性看到哪些接口越来越慢。

### 前端 JS 错误上报

如果前端页面在发请求前就报错，后端日志不会有任何记录。

这类问题需要前端错误捕获和上报。

### 数据库慢查询分析

requestId 可以告诉我某次请求慢，但不能直接告诉我是哪条 SQL 慢。

数据库慢查询还需要 query log、EXPLAIN、索引分析或 APM。

所以当前状态可以总结为：

    我已经有了基础排障线索。
    但还没有完整的主动监控、告警和趋势分析。

## 8. 下一阶段我选择什么

我选择 B：部署稳定性。

原因是：

这一阶段我刚补完基础监控和排障线索，已经能在“出错之后”更快定位问题。

但当前项目更需要补下一层能力：

    上线之前，怎么尽量减少出错？
    上线之后，怎么快速验证？
    如果上线坏了，怎么有章法地回滚或恢复？

继续做监控当然也有价值，比如慢请求日志、Sentry、uptime monitor。

但如果现在马上接第三方监控工具，我可能只是学会配置工具，还没有真正建立稳定发布的流程感。

而部署稳定性会把前面这些能力串起来：

- CI 能不能挡住明显错误
- 环境变量上线前有没有检查
- 数据库迁移有没有风险
- 前端和后端 URL 是否匹配
- CORS 是否正确
- 上线后 smoke 怎么跑
- 失败后怎么判断是否回滚

所以我选择下一阶段先练：

```text
部署稳定性：上线前 checklist、上线后 smoke、失败时回滚预案。
```

这会让我从：

    线上坏了，我怎么定位？

继续走向：

    我怎么让线上更少坏？

这是当前项目更自然的下一步。
