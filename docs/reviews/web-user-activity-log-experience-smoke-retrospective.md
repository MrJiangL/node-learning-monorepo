# 用户级 Activity Log 体验优化 smoke 和复盘

## 1. 这次我验证了什么

这次 smoke 验证的是用户级 Activity Log 体验优化是否符合预期。

重点不是后端接口是否存在，因为 `GET /activity-logs` 之前已经完成并通过线上 smoke。

这次重点是前端交互边界：

```text
1. 初始进入 /projects 时，不自动请求 GET /activity-logs
2. 用户点击“加载最近操作”后，才加载用户级 Activity Log
3. 用户已经加载过“我的最近操作”之后，Project / Todo 操作成功会自动刷新
4. idle / empty / error 文案更容易理解
```

这次验证的核心结论是：

```text
“我的最近操作”现在不是一个只会手动刷新的静态面板，
而是一个在用户主动打开后会跟随页面操作变化的最近动态区域。
```

## 2. 初始不自动加载是否合理

初始不自动加载是合理的。

原因是“我的最近操作”属于辅助信息，不是 `/projects` 首屏必须展示的数据。

进入 `/projects` 时，用户最先需要的是：

- Project 列表
- 当前 Project 下的 Todo
- 当前选中 Project 的上下文

用户级 Activity Log 更像是一个全局最近动态面板。

如果一进入页面就自动请求：

```text
GET /activity-logs
```

会增加一次首屏附加请求，但不一定每个用户都会看。

当前设计更克制：

```text
用户没有表达兴趣之前，不抢请求。
用户点过“加载最近操作”之后，再帮他保持更新。
```

这个边界比较适合当前阶段。

## 3. 加载过以后自动刷新是否自然

加载过以后自动刷新是自然的。

因为用户点击“加载最近操作”这个动作，本质上表达了：

```text
我现在关心最近操作。
```

在这个前提下，如果用户继续创建 / 编辑 / 删除 Project 或 Todo，面板自动刷新是符合预期的。

否则用户会看到一个“最近操作”面板，但它其实停留在旧数据，需要每次手动点击刷新。

现在的体验更像真实产品里的“最近动态”：

```text
用户打开它以后，它就跟着当前页面变化。
```

同时它仍然保留了一个重要边界：

```text
没有加载过就不自动刷新。
```

这避免了把辅助面板变成页面隐形的固定请求。

## 4. 文案优化是否更清楚

这次文案优化比第一版更清楚。

idle 状态从“点击加载，查看你最近的所有操作”变成：

```text
加载后可以查看你跨 Project 的最近操作。
```

这个文案更明确地告诉用户：

```text
这里不是当前 Project 的日志，而是跨 Project 的最近操作。
```

empty 状态从“你还没有最近操作记录”变成：

```text
还没有最近操作。创建 Project 或 Todo 后，这里会显示记录。
```

这个文案给了用户下一步动作。

error 状态增加了：

```text
最近操作加载失败，可以稍后重试。
```

这比只展示技术错误更友好。

用户先知道“发生了什么”和“可以怎么做”，再看到具体错误信息。

## 5. 当前还剩哪些体验问题

当前体验已经比第一版顺手，但还可以继续优化。

### 自动刷新失败的细节

现在自动刷新失败时，用户级 Activity Log 会进入 error 状态。

这对第一版可以接受。

但更细的体验是：

```text
主操作成功仍然成功。
最近操作刷新失败只影响 Activity Log 面板。
```

后续可以考虑把这类错误做得更轻，不要让用户误以为 Project / Todo 操作失败。

### metadata 展示还不够丰富

当前用户能看到：

- message
- 中文 action
- 时间
- Project 快照名

但还看不到更细的变化内容。

例如：

- Todo 标题从什么改成什么
- dueDate 从什么日期改成什么日期
- completed 从未完成变成已完成

这属于下一阶段的 metadata 展示。

### 用户级和 Project 级的视觉分工

现在两个面板都在 ProjectsPage。

后续如果页面信息越来越多，可以继续优化视觉层级：

- Project 级 Activity Log 更靠近当前 Project / Todo
- 用户级 Activity Log 更像全局侧栏或最近动态区域

## 6. 下一阶段我选择什么

下一阶段选择：

```text
A. 用户级 Activity Log 体验优化线上 smoke
```

选择原因：

- 这次改的是用户能直接感知的交互行为。
- 本地 smoke 已经完成。
- 线上还需要确认 Netlify 最新 bundle 是否包含这次优化。
- 线上还需要确认不会首屏自动请求 `GET /activity-logs`。
- 线上还需要确认加载过以后 Project / Todo 操作会自动刷新。

这一步完成后，用户级 Activity Log 的体验优化就形成完整闭环：

```text
本地实现
  -> 本地测试
    -> 本地 smoke
      -> 线上 smoke
```
