# 前端产品体验阶段复盘

## 1. 这一阶段我完成了什么

这一阶段我把前端从“能登录、能进 Project 页面”，推进到了更像真实产品入口的状态。

我完成了：

- 注册页
- 注册成功后自动登录
- 登录页和注册页互相跳转
- 路由守卫测试
- 退出登录测试
- authenticatedFetch 登录态测试
- Project / Todo 的 idle / loading / empty / error 状态展示
- 线上注册 / 登录 / 退出 smoke 复盘

这说明前端不只是能调 API，而是开始有了完整用户路径。

## 2. 注册页解决了什么问题

注册页解决的是“新用户怎么进入系统”的问题。

之前线上测试账号必须通过 API 手动创建：POST /auth/register。

这对开发者可以接受，但对真实用户不成立。

补注册页之后，用户可以直接在前端完成：

1. 输入邮箱、密码和昵称
2. 创建账号
3. 自动登录
4. 进入 Project 工作台

这里我学到的是：

前端产品体验不只是“页面能不能调用接口”，还包括用户能不能顺着页面自然完成第一步操作。

## 3. 登录态体验解决了什么问题

登录态体验解决的是“用户什么时候应该看到什么页面”的问题。

这一阶段我补了：

- 没登录访问 /projects 会回到 /login
- /login 和 /register 不需要登录
- 退出登录会清理 token
- 退出后回到 /login
- authenticatedFetch 在 401 后会尝试 refresh
- refresh 失败或没有 refreshToken 时会清理登录态

这里我学到的是：

登录态不是只有“登录成功”这一刻。

它还包括：

- token 怎么保存
- token 什么时候被带到请求里
- token 失效后怎么恢复
- 恢复失败后怎么回到可理解的状态

## 4. 状态展示解决了什么问题

状态展示解决的是“用户等待或没有数据时，页面不能沉默”的问题。

Project / Todo 页面现在覆盖了：

- idle：还没加载
- loading：正在加载
- empty：加载成功但没有数据
- error：加载失败
- success：有数据

这里我学到的是：

真实产品里，页面的大多数时间不一定是 success 状态。

如果页面没有 loading，用户会不知道是不是卡住了。

如果页面没有 empty，用户会不知道是“没有数据”还是“加载失败”。

如果页面没有 error，用户会不知道下一步该怎么排查。

## 5. 线上 smoke 让我确认了什么

线上 smoke 让我确认了这条真实路径已经跑通：

    Netlify 前端 -> Railway API -> Railway MySQL

我在线上验证了：

1. 打开注册页
2. 注册新账号
3. 自动进入 /projects
4. 创建 Project
5. 创建 Todo
6. 退出登录
7. 回到 /login
8. 再次登录
9. 回到 /projects

这说明前端、后端、数据库、CORS、token 保存、路由守卫和业务 API 已经连成一条完整链路。

## 6. 前端体验层和后端安全边界有什么区别

前端体验层主要解决：

    用户应该看到什么？
    用户下一步应该去哪？
    用户遇到等待、空数据、错误时能不能理解？

例如：

- 路由守卫把未登录用户带回 /login
- loading 文案告诉用户正在加载
- empty 文案告诉用户当前没有数据

后端安全边界主要解决：

    没有权限的请求能不能真的访问数据？
    伪造请求能不能越权？
    token 无效时能不能被拒绝？

例如：

- 后端 requireAuth 验证 token
- Project / Todo API 只返回当前用户的数据
- 后端不相信前端传来的 userId

所以：

前端路由守卫是体验层，不是安全边界。

后端鉴权才是数据安全边界。

这两个都重要，但负责的问题不同。

## 7. 我现在怎么看一个真实产品的前端体验

我现在理解的前端体验，不只是“页面能显示数据”。

它至少包括：

- 新用户能不能开始使用
- 老用户能不能登录回来
- 用户离开时能不能退出
- 没数据时页面有没有解释
- 加载时页面有没有反馈
- 出错时用户知不知道发生了什么
- 线上环境里这条路径是否真的能跑通

这一阶段让我从“写页面调接口”，开始转向“设计一条用户能走完的路径”。

## 8. 下一阶段我想选什么

我选择 B：回到生产化监控。

原因是：

前端产品体验主链路已经跑通了。现在继续补体验当然还可以，但更值得进入下一层问题：

    线上坏了，我怎么知道？
    线上哪里坏了，我怎么定位？
    用户说不能用时，我应该先看前端、API、数据库，还是日志？

我想下一阶段重点练：

- 日志怎么记录得更有用
- 请求失败时怎么定位
- 健康检查能告诉我什么
- Railway logs 应该怎么看
- 是否需要 request id / trace id 帮助串起一次请求

这会把项目从“功能能跑”继续推进到“线上更容易维护”。
